# 集数身份与多来源编号方案

日期：2026-09-29。状态：已完成代码/生产只读核查及方案；尚未实施数据库迁移或功能切换。

## 结论
内部采用稳定 episode_uid 识别同一集；季内编号作为常用显示，来源编号作为带命名空间的映射。不能只存两个无上下文整数，也不能把所有来源统一减去前一季集数。系列关联、季/篇章关联和来源编号规则均需独立。

## 已核实的问题
- 用户确认《野生的大魔王出现了！第二季》第1集对应巴哈姆特第13集，第一季12集。
- 本机媒体8821fbd4d3407124319c6c70b54cdb60绑定show_id=616808、episode=1，文件明确S02E01，mapping.season=2、offset=0、airing_offset=0。
- 2026-09-29只读GET Bangumi /v0/episodes?subject_id=616808&type=0&limit=3：章节1746074同时提供ep=1、sort=13、type=0；后续1746075为2/14、1746076为3/15。该条目total=12。
- sources.details仅保存sort，丢弃章节ID、ep、type。生产airings为13起；board直接合并episodes/watches/airings并从1循环到max，生产接口实际生成1–24格。
- engine.gaps仅局部用airing_offset；board不使用它。修改一个偏移不能统一全站。
- releases.episodes_of对所有匹配格式统一减mapping.offset：S02E01和单独13混用时会错误拒绝或错配。RSS标题、种子内文件、字幕文件还可能各用不同编号。
- auto_danmu直接比较episodeNumber与本地episode；有下载offset时直接退出，且UGC只核对季内集号，未表达来源编号体系。其自动匹配当前仍不完整支持跨季编号。
- watch.js从长标题正则抽最后一个集号展示、分集下拉按裸数字预选，缺乏统一语义。不能把巴哈13仅改文案伪装成已核验。

## 建议模型（概念字段，实施时落实迁移SQL）
1. episode_catalog：episode_uid不可变主键，show_id/season_or_part_id，本季ordinal，kind（正片/特别篇/总集篇/剧场版等），标题/播出日，可选明确系列关联。旧shows目前多为Bangumi条目，不能认定一个条目永远等于一个季度/季。
2. episode_numberings：episode_uid，scheme_id，原始label，parsed_number（允许精确小数文本），来源条目ID与来源章节ID，来源季/篇章，证据、核验状态、时间、revision。scheme_id包含provider+条目/版本范围，不能仅写bilibili/bahamut；B站按BV/合集/上传者版本定位。
3. numbering_rules：限定来源、条目/发布组、文件类型、适用区间的编号转换。支持直接身份、季内号、连续号、显式逐集表；offset只是经核验连续区间的简写。每条规则版本化，必须能追溯到证据。
4. 文件/任务/观看关联逐步增加episode_uid外键；一文件多集通过关联表表达，但第一阶段仍拒绝自动提交无法核验的一文件多集。下载版本、来源弹幕和剧集身份分离。
5. 连续集号可空、可多套；未知不能填0或默认等于季内号。只有确认所属正片序列才显示“总第13集”；否则显示“巴哈编号13”。不要从全部前作/外传/特别篇简单累加。

示例（本次目标映射）：
- 同一episode_uid，内部作品616808、本季1、季2、正片。
- 文件命名：S02E01。
- Bangumi章节1746074：ep=1、sort=13（两字段都保存原值）。
- 巴哈姆特指定条目的指定videoSn：显示13，映射同一episode_uid（实施时读取具体videoSn并保存证据）。
- B站某BV/分P：可以标S2E1或13，只有作品/季/版本/集数映射成立才绑定。
- 用户已确认本例1↔13；这个确认不能泛化为所有动画或所有平台一律offset12。

## 解析与匹配流程
原始标题/文件名/来源响应留存 → 解析作品、季、集号、编号形式 → 确定来源范围与作品条目 → 查询已核验映射 → 得到episode_uid → 去重/下载/展示。
- 标题解析产生候选而非事实；S02E13也可能为混合编号，不能仅看格式强制认定。
- 优先现有稳定章节ID和已核验映射；元数据同时提供双号是强证据，但仍校验条目/类型/唯一性/范围，不能对所有条目无条件用ep替换sort。
- 日期、章节标题、季关系与连续覆盖用于交叉核验；最小编号13或上一季total12只能提出候选，不能独立授权。
- 同一集出现两个来源编号时是别名；同一来源编号指向多集则冲突，不自动覆盖。改版/合并版保留版本差异。
- 资料自动修订可新增建议，不能静默重绑已下载文件、覆盖人工观看、重新授权或改变清理墓碑。
- 仅同名、短简称、无季信息的“第1集”不能跨季自动匹配。
- 特别篇、0集、12.5、分割放送、后半篇、合集/拆分版、番外、重制版单独建模；一季跨季度不会自动变新季。
- 剧集身份匹配和弹幕秒数对齐是两件事；B站尾部加长不改变集号身份，不按总时长缩放。

## 页面显示约定
- 标题：第二季 · 第1集；已确认连续编号时次级显示“连续第13集”。
- 巴哈源：本集 · 平台第13集；B站源：本集 · 平台第1话。更多信息可看原始标题与映射依据。
- 集列表本季1–12。可搜索S02E01、第二季1、已核验连续13，结果指向同一集。
- 源号尚未核验则标待核对，不显示“本集”。编号offset用“集数映射”；弹幕offset用“提前/延后（秒）”，绝不共用字段。

## 建议落地顺序
A. 身份/映射表+纯resolver+元数据原始字段；临时DB迁移演练、生产只读差异报告。本例作为明确测试基准。
B. 先修airings/board/显示和弹幕读取，保留原旧键兼容；不能在其他消费者未转换时只改episodes的数字。
C. 下载解析、缺集、种子选文件、字幕和旧库统一接入resolver，影子运行比较新旧选择；确认一集一版不变后切换新任务。
D. 已有episodes/watches/history绑定episode_uid，冲突报告；保留手工记录和老映射快照。完成后逐步废弃全局offset/airing_offset。
迁移幂等、事务、版本号和备份；从存量明确S02E01/已关联条目回填，不把历史13全表减12。不得触发补下、改变追番/授权、删除媒体或重建在途下载。

## 验收案例
- 本例S02E01 / Bangumi ep1-sort13 / 巴哈13 / B站1或13绑定一集；本季只有12格，播出日期落第1格。
- 混合来源S02E01与13不重复下载；第一季01不串入第二季01。
- 同一发布标题13、内文件S02E01、字幕13经已核验规则能选中；无映射则待查。
- S2E1看完只改变这一集，原播放位置/手动未看保留；显示编号修改不变观看状态。
- 特别篇12.5、第二部分、跨季连续号、多集文件、不同重制版不能被简单offset合并。
- 新旧转换冲突、远端元数据修改、离线/部分章节缺失不重绑文件或自动补下。
- 迁移运行两次结果不变；在途任务按旧manifest完成仍落同一身份；旧文件及cleanup_hold保持边界。
